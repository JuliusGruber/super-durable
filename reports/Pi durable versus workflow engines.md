# Engines supply orchestration; pi-durable supplies sessions

For a single TypeScript developer who self-hosts, pi-durable and the four workflow engines cover opposite halves of the Super-agent, and none covers both. pi-durable is the only one of the five whose durable object is the agent session itself: a persisted transcript and an inbox that queues and batches input during a turn, plus a remote tool executor. Temporal, Restate, DBOS and Inngest instead supply what pi-durable leaves as glue (addressing another session by ID, asynchronous Workers, schedules, an external control plane, event dedup), and all four leave the session, its inbox, the transcript store and compaction to application code. All four also push a months-long Router away from "one long run" toward "one short run per turn over state the application owns", either through hard limits (Temporal, Inngest) or through upgrade and history-growth problems (DBOS, Restate). Among the engines, **Restate is the closest architectural fit** (a keyed Virtual Object with indefinite state, and a first-party TypeScript reference agent that already implements queued input, steering and compaction), **DBOS is the lightest to adopt** (an MIT library plus Postgres), **Temporal is the most complete and the heaviest**, and **Inngest fits the Router worst** despite the best event ingestion. The recommendation: stay on pi-durable if the Router's behaviour is what is being explored, and move to Restate or DBOS if Workers, the Watchdog and operations turn out to be the main cost. This is a comparison of documentation and repository contents as of 14 November 2026; nothing was built or run on any of the five, and no published router/worker/watchdog build was found on any of them.

## The five substrates split along one line: who owns the session

The Super-agent article asks for a Router that is one long-lived LLM session, queues Triggers that arrive during a turn and handles them together in the next turn; Workers that run in isolation and report back as new events; a Watchdog outside the main system on a schedule; Trigger filtering in code before any model call; and tools that execute on remote machines ([X article](https://x.com/DeepSeekHarness/status/2116857257245987236)). The table shows where each substrate provides a mechanism and where the developer writes it.

| Requirement | pi-durable | Temporal | Restate | DBOS | Inngest |
|---|---|---|---|---|---|
| Months-long Router session | Native conversation; compaction unchecked | Entity workflow with Continue-As-New; transcript external | Virtual Object state; one invocation per turn | Per-turn workflows over app tables, or a pinned long workflow | App database plus a session key; one run per turn |
| Queue and batch input during a turn | Native inbox with batch modes | Signal handler plus hand-written queue | Controller object plus signals; reference agent has it | `send`/`recv` loop, one message per `recv` | App inbox table; no native mapping |
| Asynchronous isolated Workers | Glue: anchor and reporter tasks | Native: child or separate workflow, Signals back | Native sends, cancel; report-back by one-way send | Native: `startWorkflow`, queues, `send` to parent | Native start and cancel; report-back needs the app inbox |
| External Watchdog | Read-only from a second process; act only through the owner; no scheduler | Schedules plus full read and intervene by ID | Delayed self-send; SQL introspection; admin API | Cron, listing, cancel, resume, fork from any process | Cron plus REST control plane; no steer |
| Code-level Trigger ingestion | Host code | App server plus Signal-With-Start | HTTP ingress with idempotency key | App server; workflow ID as dedup key | Hosted webhooks, transforms, 24 h dedup |
| Remote tool execution | pi-env daemon over SSH | Application code in Activities | Out of scope | Application code | Application code |
| Self-hosted footprint | 1 Node process, 1 SQLite file | Server, UI, database, plus app processes | 1 server binary plus 1 Node process | 1 Node process plus Postgres | 1 server binary (beta) plus 1 Node process |

pi-durable's column is strong exactly where the others are weak. A pi-durable conversation accepts input while a run is active and queues it in a persisted inbox; `whenBusy: steer` with `steeringMode: all`, or `followUpMode: all`, delivers the queued items as one batch ([pi-durable spec](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md)). That is the article's Router batching without application code. The price is everything around it: no built-in subagent API, no scheduler on a Node host, no event bus, and a single-writer storage that a second process can read but not write ([pi-durable README](https://github.com/earendil-works/pi/tree/main/packages/durable)). The engines invert this. Each documents its agent support as "wrap the model and tool calls in durable steps", and each leaves the transcript and the inbox to the application: DBOS's Vercel AI integration persists messages through a user-defined `saveMessage` ([DBOS Vercel AI integration](https://docs.dbos.dev/integrations/vercel-ai)), Inngest recommends "a separate memory store keyed by conversation or user ID" ([Inngest durable agents](https://www.inngest.com/docs-markdown/durable-execution/durable-agents)), Restate's TypeScript sessions read and write history with `ctx.get` and `ctx.set` ([Restate durable sessions](https://docs.restate.dev/ai/patterns/sessions.md)), and Temporal's integration pages do not cover conversation history at all ([Temporal AI SDK integration](https://docs.temporal.io/develop/typescript/integrations/ai-sdk.md)).

One property is shared by all five and should not drive the choice: **side effects are at-least-once everywhere**. Temporal says an Activity "may be executed multiple times" ([Temporal activity definition](https://docs.temporal.io/activity-definition)), DBOS steps are "tried at least once" ([DBOS workflow tutorial](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial)), Inngest warns that "a step can succeed externally before its result is saved" ([Inngest execution model](https://www.inngest.com/docs/learn/how-functions-are-executed)), and Restate retries failed `ctx.run` steps ([Restate journaling](https://docs.restate.dev/develop/ts/journaling-results.md)). pi-durable differs only in the default: tools not marked `replay: safe` are not rerun after an interruption and return an interrupted result to the model instead ([pi-durable spec](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md)). For tools that open pull requests or run remote commands, idempotency keys or reconciliation are needed on every substrate.

## No engine lets the Router be one months-long run

The engines differ in why a single long run fails, and the reason shapes the design.

**Temporal terminates the run.** An execution is terminated at **51,200 events or 50 MB of history**, any single payload is capped at **2 MB**, and the same values are the self-hosted defaults ([Temporal Cloud limits](https://docs.temporal.io/cloud/limits); [self-hosted defaults](https://docs.temporal.io/self-hosted-guide/defaults)). A never-ending Router must therefore be an entity workflow that periodically calls Continue-As-New, carrying its state into a fresh run under the same Workflow ID ([Continue-As-New](https://docs.temporal.io/workflow-execution/continue-as-new)). Three consequences follow. The transcript cannot be workflow state, because the carried input is itself subject to the 2 MB limit, so a transcript store is application-built or relies on an external-storage converter still marked experimental ([sdk-typescript releases](https://github.com/temporalio/sdk-typescript/releases)). Child workflows "do not carry over" a parent's Continue-As-New ([child workflows](https://docs.temporal.io/child-workflows)), so Workers must be independent or abandoned. And workflow code can change only "in very limited ways" while an execution depends on it ([workflow definition](https://docs.temporal.io/workflow-definition)), so versioning becomes a standing duty for a session that spans every deployment. Batching itself is straightforward: Signal handlers run interleaved with the main function at `await` points ([TypeScript message passing](https://docs.temporal.io/develop/typescript/message-passing)), so a handler appends to an array and the loop drains it after the LLM Activity returns. The notes found no TypeScript example of this pattern; it is an inference from documented behaviour.

**Inngest caps the run.** A run is limited to **1,000 steps, 32 MiB of state** and 30, 90 or 366 days of life depending on plan ([Inngest usage limits](https://www.inngest.com/docs/usage-limits/inngest)); whether a self-hosted server enforces these is unconfirmed. More decisive is the input model. A run receives input only while parked in `step.waitForEvent`, and "the wait only sees events sent after it begins listening" ([waitForEvent](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/wait-for-event)), so events sent during an LLM step are lost unless written elsewhere. Native batching is a time and size window, not "what arrived during the last turn", and it cannot be combined with singleton, debounce, cancellation events or idempotency ([batching](https://www.inngest.com/docs/guides/batching)). The only design that gives the article's semantics is an application inbox table drained by one function per session. Inngest's own example agent takes the other route: a new message cancels the running turn and restarts it ([utah message.ts](https://github.com/inngest/utah/blob/main/src/functions/message.ts)).

**DBOS states no limit, but field evidence argues against the long workflow.** `DBOS.send` persists messages regardless of what the receiver is doing and `DBOS.recv` returns one at a time ([DBOS workflow communication](https://docs.dbos.dev/typescript/tutorials/workflow-communication)), so a `recv` loop gives queue-while-busy with batching by looping until empty. The obstacles are upgrades and growth. Recovery "only recovers workflows whose version matches the current application version", the version defaults to a hash of the workflow source, and automatic upgrade of pending workflows is an Enterprise feature ([upgrading workflows](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows)). The one third-party runtime that ships a persistent-session mode on DBOS reports roughly O(N²) storage growth for long sessions, says such workflows "must be cancelled before rollout", and makes one short workflow per turn its default ([Helix Agents DBOS runtime](https://agents.open-source.onhelix.ai/runtimes/dbos.html)). In that per-turn shape the inbox moves to an application table, and DBOS adds queues and recovery around what is otherwise a plain Node-and-Postgres agent.

**Restate designs for short invocations from the start.** A Virtual Object's state is "retained indefinitely", and only one writing handler runs per key ([Restate services](https://docs.restate.dev/foundations/services.md)). Further calls wait in a per-key inbox and are dispatched one at a time, so batching is again application code. Restate is the one engine that publishes that code. Its TypeScript reference agent splits each agent into a short-lived controller object and a session object, queues `ask` input while busy, and has `steer` drain queued input into a durable signal for the running turn ([restatedev/agent architecture](https://raw.githubusercontent.com/restatedev/agent/main/docs/architecture.md)); it also compacts history once the context passes 60% of the window ([turn runtime](https://raw.githubusercontent.com/restatedev/agent/main/docs/turn-runtime.md)). This is the nearest thing in any engine to pi-durable's inbox modes, with two caveats: it is a reference repository of 15 stars and no visible licence or package, and it rests on ordered multi-delivery signals that arrived in SDK v1.18.0 on 28 October 2026 ([sdk-typescript releases](https://github.com/restatedev/sdk-typescript/releases)).

pi-durable's own long-session risks are different in kind, not absent. Context compaction was never checked in the earlier research, conversations cannot be deleted, and the package is labelled experimental with an API that changes between releases ([pi-durable README](https://github.com/earendil-works/pi/tree/main/packages/durable)). Its batch mode is also a Harness-wide setting ([harness types](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/types.ts)), so a Router and Workers in one Harness share it.

## Workers, Watchdog and Triggers are where the engines pay back

These are pi-durable's glue rows, and each engine closes at least two of them with documented primitives.

**Workers.** On pi-durable a non-blocking `start()` needs an anchor background task that owns a child conversation and a reporter task that posts the answer back as a follow-up input, deduplicated by request ID; the pattern exists as a runnable example ([22-subagent-background.ts](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/22-subagent-background.ts)). Temporal makes this a few calls: start a child with Parent Close Policy Abandon, which is "useful for starting Child Workflows asynchronously" ([parent close policy](https://docs.temporal.io/parent-close-policy)), signal the Router's Workflow ID with the result, and request cancel for `stop()`. DBOS is as direct and adds the article's worker slots for free: `startWorkflow` returns a handle once the child is durably started ([DBOS methods](https://docs.dbos.dev/typescript/reference/methods)), queues enforce global concurrency ([queue tutorial](https://docs.dbos.dev/typescript/tutorials/queue-tutorial)), and a `send` from inside a workflow is exactly-once. Restate has one-way sends, invocation IDs and `ctx.cancel` ([service communication](https://docs.restate.dev/develop/ts/service-communication.md)), though all its published multi-agent material has the parent wait for the child ([multi-agent orchestration](https://docs.restate.dev/ai/patterns/multi-agent.md)). Inngest starts Workers with `step.sendEvent` and stops them with `cancelOn`, but the report-back lands in the same application inbox the Router needs anyway; Inngest's own async sub-agents reply to the user, not to the parent ([three sub-agent patterns](https://www.inngest.com/blog/three-patterns-you-need-for-agentic-systems)).

**Watchdog.** pi-durable gives a Watchdog process a read-only view: a second process can open the same SQLite storage as a viewer, while writes and `resume()` reject with `ReadOnlySession` ([harness types](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/types.ts)). To steer, abort or submit `continue` it must call an API on the owning process that the developer designs, and the schedule is also the developer's. Every engine does better on the mechanics. Temporal Schedules start a workflow on an interval ([schedule](https://docs.temporal.io/schedule)) and any client can describe, query, signal, cancel, terminate or reset any execution by ID ([workflow CLI](https://docs.temporal.io/cli/workflow)). DBOS offers cron schedules ([scheduled workflows](https://docs.dbos.dev/typescript/tutorials/scheduled-workflows)), `listWorkflows`, `listWorkflowSteps` with per-step timestamps, and cancel, resume and fork ([workflow management](https://docs.dbos.dev/typescript/tutorials/workflow-management)), all usable from a second process holding only the database URL. Restate has no built-in cron ([cron guide](https://docs.restate.dev/guides/cron.md)) but exposes invocations, journals, inboxes and object state over SQL ([introspection](https://docs.restate.dev/services/introspection.md)). Inngest pairs cron triggers with a REST API for run status, cancel and replay ([REST API v1](https://api-docs.inngest.com/api-specs/v1.json)). No engine detects "running but drifting". That judgement stays an LLM call over a transcript the application stores, on all five.

**Triggers.** Inngest leads: per-environment webhook URLs with a JavaScript transform, allow and deny lists, and 24-hour dedup by event ID, although it "does not verify provider webhook signatures" ([Inngest webhooks](https://www.inngest.com/docs/platform/webhooks)) and whether webhooks exist on the self-hosted server is unconfirmed. Restate accepts fire-and-forget calls on its HTTP ingress with an `Idempotency-Key` header retained for 24 hours ([HTTP invocation](https://docs.restate.dev/services/invocation/http.md)). Temporal and DBOS need an application HTTP server in front, as pi-durable does, and contribute dedup keys: Workflow IDs and Update IDs on Temporal ([workflow ID](https://docs.temporal.io/workflow-execution/workflowid-runid)), workflow IDs and `send` idempotency keys on DBOS. Thread subscriptions, the two-stage filter and Chain of Recall are application tables and prompts on every substrate.

**Remote tools.** Here pi-durable stands alone. `@earendil-works/pi-env` is a Rust daemon deployed and started over SSH for Linux, macOS, Android and Windows, and a pi-durable execution environment that talks to it ([pi repository, packages/env](https://github.com/earendil-works/pi/tree/main/packages/env)). It dials in to the endpoint and has no offline queueing, so it does not match the article's outward-connecting daemon. No engine ships an equivalent; Restate's reference agent offers a local workspace or Modal, and Inngest Sandboxes are hosted microVMs in beta ([Inngest sandboxes](https://www.inngest.com/docs-markdown/sandboxes/overview)). By inference only, a Temporal worker or an Inngest `connect` worker running on the endpoint would connect outward and pick up queued work on reconnect, which is closer to the article's shape than pi-env, but neither is a documented pattern.

## Self-hosting costs range from one file to four services

For one developer the operating burden separates the options more than features do.

pi-durable needs one Node process (22.19 or later) and one SQLite file, plus an external supervisor to restart the process ([pi-durable README](https://github.com/earendil-works/pi/tree/main/packages/durable)). **DBOS adds only Postgres**: the TypeScript library does not support SQLite, runs no orchestration server and is MIT-licensed ([DBOS configuration](https://docs.dbos.dev/typescript/reference/configuration); [dbos-transact-ts](https://github.com/dbos-inc/dbos-transact-ts)). What it holds back for payment is modest at this scale: automatic failover between processes, retention policies and the web console sit in Conductor from $99 a month, and `suspend` and auto-upgrade need an Enterprise key ([DBOS pricing](https://www.dbos.dev/dbos-pricing)). **Restate adds one server binary** with a persistent volume and no external database; a minimal setup uses about 1.5 GiB of memory ([Restate server memory](https://docs.restate.dev/server/memory.md)). Its server is under the Business Source License 1.1, which permits private self-hosting and excludes offering a public Restate platform ([Restate LICENSE](https://github.com/restatedev/restate/blob/main/LICENSE)). **Inngest adds one binary too**, but `inngest start` is labelled beta, keeps queue and run state in an in-process Redis with periodic snapshots, prunes nothing automatically and carries no support commitment ([Inngest self-hosting](https://www.inngest.com/docs/self-hosting)); crash-safe run state means adding an external Redis. **Temporal is the heaviest**: the server and UI binaries plus PostgreSQL, MySQL or Cassandra ([self-hosted deployment](https://docs.temporal.io/self-hosted-guide/deployment)), since the single-binary dev server with SQLite is "meant only for development and testing" ([persistence](https://docs.temporal.io/temporal-service/persistence.md)). Its escape hatch is Temporal Cloud with no base fee at $50 per million Actions ([Temporal pricing](https://temporal.io/pricing)), which abandons the self-hosting premise.

Maturity cuts the other way. Temporal's TypeScript SDK has been 1.x since 2022 and is at v1.25.0, though its agent integrations, Workflow Streams and external storage are all 2026 additions whose status labels still conflict between blog and docs ([Temporal AI integrations post](https://temporal.io/blog/ai-framework-integrations)). Restate's SDK is at v1.18.3 and DBOS at v5.5, the latter two months after a breaking v5.0 and with its only TypeScript agent integration at 0.5.4 ([DBOS releases](https://github.com/dbos-inc/dbos-transact-ts/releases)). Inngest's agent library AgentKit has had no release since November 2025 ([agent-kit releases](https://github.com/inngest/agent-kit/releases)). pi-durable is the least settled: experimental, at 1.5.2, with signals, parking tools and approval gates only on `main` ([pi repository](https://github.com/earendil-works/pi)).

The steelman for each loser deserves a line. Temporal wins if the system grows beyond one developer, because its limits, versioning and tooling are the best documented. Inngest wins if webhook reception without a public endpoint matters and its cloud free tier is acceptable. Neither premise matches a single developer who self-hosts.

## Conclusion

The comparison changes the question from "which substrate" to "which half do you want to write". On pi-durable the developer writes orchestration: Worker lifecycle, a Watchdog control API, scheduling and ingestion. On any engine the developer writes the session: inbox, transcript store, compaction and turn state machine. The engines' own agent examples all settle on short durable turns over application-owned state, which is close to the plain Node-and-database baseline the earlier blind-spot analysis asked for, with recovery and queues added. That makes DBOS in per-turn mode the cheapest experiment to run beside pi-durable, and Restate's reference agent the cheapest way to see a complete session layer built on an engine.

The layers also separate more cleanly than the framing suggests. Inngest's example agent uses pi-ai, the same model layer as pi-durable, inside Inngest steps ([inngest/utah](https://github.com/inngest/utah)), and pi-env is a standalone package, so a Router on pi-durable with Workers or a Watchdog on an engine, or an engine-hosted loop that borrows pi-env for remote tools, are both plausible. None of this is tested. Three unconfirmed points would move the ranking if they resolved badly: whether Restate signals still need an experimental protocol flag, whether DBOS garbage collection works without Conductor, and whether pi-durable compacts context at all. A spike that kills the process mid-turn on pi-durable and on one engine would settle more than further reading.
